# Internationalization (i18n)

The site is translated with [next-intl](https://next-intl.dev) and exported as
static HTML.

| Locale | Language   | URL prefix | Messages           |
| ------ | ---------- | ---------- | ------------------ |
| `en`   | English    | none       | `src/messages/en/` |
| `pt`   | Portuguese | `/pt`      | `src/messages/pt/` |
| `dz`   | Dzongkha   | `/dz`      | `src/messages/dz/` |
| `hi`   | Hindi      | `/hi`      | `src/messages/hi/` |

English is the source language and the default locale. It keeps the existing
unprefixed URLs (`/about`); the other locales are served under their prefix
(`/pt/about`). Locale metadata (native names, `<html lang>`, `og:locale`) lives
in `src/i18n/config.ts`.

## How it fits together

- `src/app/[locale]/` holds every page. Pages read the locale from `params`.
- `src/app/(default)/` holds the English routes. Each `page.tsx` there is a
  generated one-line re-export of the `[locale]` page, rendered without a
  `locale` param, which resolves to English. Don't edit these by hand.
- `src/app/[locale]/layout.tsx` is the root layout for all locales; the
  `(default)` layout re-exports it. Both render `RootDocument` from
  `src/components/root-document.tsx` (`<html lang>`, fonts, site metadata).
- Because there is no single top-level layout, the 404 page is
  `src/app/global-not-found.tsx` (enabled with `experimental.globalNotFound`).
  Static hosts serve that one `404.html` for every locale, so it is English.
- `src/messages/en/<namespace>.json` is the English catalog, one file per
  namespace. `src/i18n/en-catalog.generated.ts` imports them all and provides
  the message types.
- `src/messages/<locale>/<namespace>.json` are translations with the same
  shape. Missing namespaces, keys or empty strings fall back to English.
- `npm run i18n:sync` regenerates the catalog index and the `(default)` routes.
  It runs automatically before `npm run dev` and `npm run build`.
- `npm run i18n:check` validates every catalog (see [Checking translations](#checking-translations)).

## Writing a page

Every page and layout calls `initLocale(params)` first. Static export fails
with a "used `headers`" error if a page renders translations without it.
Metadata is translated in `generateMetadata` with `pageMetadata()`, which adds
the canonical URL, `hreflang` alternates and `og:locale`.

```tsx
import { pageMetadata } from '@/i18n/metadata'
import { initLocale, resolveLocale, type PageProps } from '@/i18n/server'
import type { Metadata } from 'next'
import { useTranslations } from 'next-intl'
import { getTranslations } from 'next-intl/server'

export async function generateMetadata({
  params,
}: PageProps): Promise<Metadata> {
  const locale = await resolveLocale(params)
  const t = await getTranslations({ locale, namespace: 'about.meta' })

  return pageMetadata({
    locale,
    path: '/about', // the unprefixed route of this page
    title: t('title'),
    description: t('description'),
    keywords: 'Open Healthcare Network Foundation, ...', // keywords stay in English
  })
}

function Hero() {
  const t = useTranslations('about.hero') // hooks work in sync server components
  return <h1>{t('title')}</h1>
}

export default async function About({ params }: PageProps) {
  await initLocale(params)
  return <Hero />
}
```

- Pages with more params type them as `PageProps<{ slug: string }>`.
- In `async` server components use `await getTranslations('namespace')`. In
  sync server components and client components use `useTranslations`.
- Keep `title` short: the layout appends ` - Open Healthcare Network`.
- A page that re-exports another page (`/company` → `/about`) re-exports
  `default` and `generateMetadata`.

`src/app/[locale]/page.tsx` (home), `src/components/navbar.tsx` and
`src/components/footer.tsx` are complete examples.

## Message conventions

**Namespaces.** One namespace per route, named after the path in camelCase:
`/` → `home`, `/about/team/foundation` → `aboutTeamFoundation`,
`/solutions/care-clinics` → `solutionsCareClinics`. Shared components get a
namespace named after the component (`footer`, `faqSection`). Navigation labels
live in `nav.links` and are reused by the footer.

**Keys.** Nest by section (`hero.title`, `pricing.items.basic.description`),
camelCase, describing the role of the text rather than repeating it. Page
metadata goes under `meta` (`title`, `description`, `ogDescription`,
`ogImageAlt`, `twitterDescription`, only those the page uses).

**Lists.** Keep non-text data (hrefs, icons, images, ids) in code and the text
in messages:

```ts
const solutions = [
  { id: 'hmis', href: '/solutions/hospital-management', icon: Hospital },
  { id: 'teleicu', href: '/solutions/teleicu', icon: Activity },
] as const

solutions.map(({ id }) => t(`items.${id}.title`)) // keys stay type-checked
```

A list of plain strings (bullet points, table cells) can be a JSON array read
with `t.raw('modules') as string[]`. `t.raw` returns the text as-is, so use it
only for text without placeholders or markup, and render it as text, never as
HTML. Never put an array of objects in a catalog: next-intl's key types reject
the whole namespace. Key such lists by id instead
(`faq.items.<id>.question`). Any array also loosens key checking for the
object that contains it, so nest string arrays inside a section
(`care.modules`), never at the top level of a namespace.

**Inline markup.** Links, emphasis and line breaks inside a sentence use rich
text, so translators can move them within the sentence:

```json
"body": "Read the <link>governance charter</link> or <strong>contact us</strong>.",
"title": "Help steward open healthcare <br></br>infrastructure for the long term."
```

```tsx
{
  t.rich('body', {
    link: (chunks) => <Link href="/foundation/governance">{chunks}</Link>,
    strong: (chunks) => <strong className="font-semibold">{chunks}</strong>,
  })
}
{
  t.rich('title', { br: () => <br className="hidden sm:block" /> })
}
```

Tag names are free-form, but every tag needs a closing tag (`<br></br>`). Never
split one sentence into several messages around a link.

**Placeholders.** Interpolate values with `{name}`:
`t('copyright', { year: String(year) })`. Pass years, version numbers and
identifiers as strings; numbers passed as numbers are formatted for the locale
(`2,026`). Counts use ICU plurals:
`"{count, plural, one {# question} other {# questions}}"`.

**ICU syntax.** Messages are ICU MessageFormat. `{` and `}` are syntax, and an
apostrophe directly before them escapes them. Keep code snippets, JSON, shell
commands and anything else with braces in code, not in messages. Normal
apostrophes in prose (`don't`) are fine.

**What stays in code.** URLs, email addresses, phone numbers, postal
addresses, people's names, code samples, terminal commands, file names,
version numbers, and `keywords` metadata. Product names (CARE, CARE Core,
TeleICU, Care Janwar), standards (FHIR R5, SNOMED CT, LOINC, ABDM) and
organization names stay untranslated inside translated sentences; standalone
labels made only of these can stay in code.

**What goes in messages.** All visible prose and UI labels, `alt` text,
`aria-label`, `title` attributes, `placeholder`s and page metadata.

## Links

Write internal links without a locale and render them with
`@/components/link` (or `Button`, which uses it). It adds the current locale
prefix: `<Link href="/about">` goes to `/pt/about` on Portuguese pages. Don't
use raw `<a href="/...">` or `next/link` for internal pages. Where a URL is
built outside a link component, use `localizePath(href, locale)` from
`@/i18n/paths`. Files in `public/` (`/funding.json`), external URLs and
`mailto:` links are left unchanged.

## Client components

Only the `nav` namespace is sent to the browser on every page. For a client
component:

1. Prefer passing translated strings as props from the server parent (see
   `FaqSection` → `FaqList`).
2. If it needs many strings, wrap it in
   `<ClientMessages namespaces={['blogArchive']}>` (from
   `@/components/client-messages`) and call `useTranslations('blogArchive')`
   inside. Wrap the smallest subtree that needs them.

## Dates and numbers

Format dates with the shared formats in `src/i18n/request.ts`:

```tsx
const format = useFormatter() // or await getFormatter() in async components
format.dateTime(new Date(post.publishedAt), 'short') // Sep 7, 2026
format.dateTime(date, 'long') // Monday, September 7, 2026
format.dateTime(date, 'month') // September 2026
```

Dates are formatted in UTC, so the output doesn't depend on the build machine.

## Blog

Blog posts in `content/blog/` are written in English. Translated locales list
and render the English posts inside translated page chrome. Post text is
marked `lang="en"`, and post pages on every locale point their canonical URL
at the English post.

## Checking translations

```bash
npm run i18n:check
```

It fails when a catalog has invalid ICU syntax, or when a translation is
missing keys, has a different number of list items, or uses different
`{placeholders}` or `<tags>` than English. It also reports how many messages
are identical to English. Add `-- --locale hi --verbose` to list them for one
locale.

## Translator notes

- Translate meaning for a public-health audience (ministries, hospitals,
  clinicians, funders). Keep the tone plain and factual.
- Keep product, standard and organization names in English (see above).
- Keep every `{placeholder}` and `<tag>` exactly; reorder them as the grammar
  needs. Keep list lengths the same as English.
- Portuguese uses Brazilian conventions (`pt-BR`). Dzongkha uses Tibetan script
  and Dzongkha Development Commission spelling where possible. Hindi uses
  Devanagari, with common English technical terms where Hindi readers expect
  them.
- Machine-assisted translations must be reviewed by a fluent speaker before
  release, especially for Dzongkha.

## Adding a locale

1. Add it to `locales` and `localeInfo` in `src/i18n/config.ts`.
2. If it uses a new script, add a font fallback in
   `src/app/[locale]/layout.tsx` and the font stacks in
   `src/styles/tailwind.css`.
3. Create `src/messages/<locale>/` mirroring `src/messages/en/`.
4. Run `npm run i18n:check` and `npm run build`.
